Contract Gen: Verification-Driven OCL Contract Generation
Generating contract-level Object Constraint Language (OCL) specifications from natural-language requirements remains difficult
because useful contracts must do more than resemble well-formed text. They must parse, respect the target model context, translate
into executable checks, and pass downstream validation. Although large language models can produce plausible OCL fragments,
their outputs often contain syntax errors, invalid navigation paths, unresolved context references, or behavior-level inconsistencies.
One-shot generation therefore provides limited assurance for OCL operation contracts that must be executable and verifiable.
This paper formulates natural-language-to-OCL contract generation as a verification-driven synthesis problem and presents
Contract Gen, a closed-loop framework that uses validation evidence to guide bounded regeneration. Contract Gen separates
candidate generation, contract assembly, executable translation, and diagnostic classification, so that parser and TypeScript failures
become structured repair signals rather than post-hoc rejection outcomes. To ground this loop in executable behavior, we develop
OCLTSVM, a lightweight backend that parses generated OCL, constructs a typed intermediate representation, lowers accepted
contracts into TypeScript, performs static checking, and executes generated code against test scenarios.
We evaluate Contract Gen on 114 operations from five representative case studies, with comparisons against historical OCL-
generation baselines, controlled PureLLM variants, no-feedback ablations, and a USE-based sanity check. Several Contract Gen variants
reach 100% syntactic validity within five attempts, and the highest-performing variant reaches 61.40% execution-grounded validation
success. The results show that verification-guided revision improves parser-level validity and executable success for stronger backbone
models, while the remaining syntax-execution gap indicates that semantic consistency, model-context alignment, and oracle strength
remain central challenges for fully executable OCL contract generation.

1 Introduction
Model-driven development (MDD) helps manage the complexity of modern software systems by raising the level of
abstraction [11, 17]. Within MDD, the Object Constraint Language (OCL) is widely used to specify semantic constraints,
queries, and operation contracts that cannot be captured by structural models alone [9, 31]. For requirements-level
validation, the most useful artifact is often not an isolated predicate, but a complete operation contract that states what
must hold before an operation and what must hold after it executes. In practice, however, authoring suchcontract-level
OCL remains difficult. Preconditions, postconditions, and invariants are sensitive to model context, including types,
navigation paths, collections, and undefined values, and small errors can make a contract unparsable or non-executable
[1, 4, 32]. As a result, deriving OCL operation contracts from natural-language requirements requires not only syntactic
generation, but also evidence that the generated contract can be checked and executed.
Large language models (LLMs) provide a promising direction for automating OCL generation from natural-language
requirements [1, 32]. However, one-shot generation remains unreliable for artifacts that must satisfy a formal syntax
and an executable semantics. Generated contracts may be syntactically invalid, inconsistent with the target metamodel,
or brittle under execution, which is consistent with broader evidence on the correctness limitations of LLM-based
code generation [7, 13, 14]. Prior OCL generation work has mainly improved how prompts, paths, or learned models
produce OCL-like text [1, 2, 4, 32], while executable OCL backends have mainly focused on compiling or running

underexplored: when a generated contract fails, the system should turn parser, type, and execution evidence into
targeted revision signals. This gap motivates treating OCL contract generation as a verification-driven synthesis task
rather than as surface-form text generation.
Contract Gen addresses this failure mode by making validation evidence part of the generation process. Rather than
asking an LLM to produce a final contract in one step, the framework organizes synthesis as a closed loop over four
roles: anOCL Generatordrafts a candidate contract from the natural-language description and project guidance, a
Contract Generatorassembles and parses the OCL contract, aTypeScript Generatorlowers the parsed OCL AST
into executable TypeScript, and aTypeScript Parserchecks the generated code before runtime testing. When OCL or
TypeScript validation fails, the resulting diagnostics are classified, collected as reusable error evidence, and fed back to
guide another generation round within a bounded budget. This design makes validation evidence part of the generation
state, rather than treating validation as a post-hoc filter.
The loop requires a backend that can do more than reject malformed text. Contract Gen is therefore supported by
OCLTSVM, a lightweight OCL validation backend that translates OCL operation contracts into executable TypeScript
and validates them in runtime environments. The backend follows the same general principle as executable code-
generation evaluation: a candidate is credible only when it survives concrete downstream checks, not merely when
it resembles a reference string [ 7, 14]. Beyond checking executability, OCLTSVM supports source-aware localized
diagnostics at the sub-expression level, improving the interpretability of validation outcomes and providing a basis for
finer-grained revision in future extensions. This execution-grounded validation mechanism strengthens the reliability
of the overall workflow.
We evaluate the proposed approach on 114 operations from five representative case studies and compare it with
prompting-based generation baselines. The results show that verification-driven iterative regeneration improves
parser-level validity and, for the strongest backbone models, improves execution-grounded success: several Contract
Gen variants reach full syntactic validity within five attempts, and the highest-performing variant reaches 61.40%
execution-grounded validation success. The results also show a substantial syntax–execution gap, indicating that
semantic consistency, model-context alignment, and oracle strength remain central challenges.
Contributions.This paper makes the following contributions:
(1) We formulate natural-language-to-OCL contract generation as averification-driven synthesisproblem. Instead
of treating generated OCL as text to be matched against a reference, the proposed formulation requires a candidate
contract to pass successive parser-level, translation-level, static, and execution-grounded checks.
(2) We presentContract Gen, a closed-loop contract synthesis framework that converts validation failures into
structured repair evidence. The framework separates candidate generation, contract assembly, executable translation,
and diagnostic classification, allowing parser and TypeScript feedback to guide bounded regeneration.
(3) We developOCLTSVM, a lightweight execution-grounded validation backend for generated OCL operation
contracts. OCLTSVM parses assembled OCL, constructs a typed intermediate representation, lowers accepted contracts
into TypeScript, performs static checking, and executes generated code against test scenarios to produce stage-localized
diagnostics.
(4) We provide an empirical evaluation on 114 operations from five case studies. The evaluation compares Contract
Gen with historical OCL-generation baselines, controlled PureLLM variants, and no-feedback ablations, and further
includes a USE-based sanity check. The results show that parser-level validity alone is insufficient, and that diagnostic
feedback improves executable success for stronger backbone models under a fixed attempt budget.

2 Related Work
Contract Gen sits at a boundary that has usually been treated in separate literatures. Natural-language-to-OCL work
studies how to produce constraints, agentic generation studies how to revise uncertain LLM outputs, and OCL execution
backends study how to run or compile formal specifications. The gap addressed here appears when these concerns
must be handled together: a generated operation contract must be produced, checked, diagnosed, and revised under
executable evidence.
2.1 Natural-Language-to-OCL Generation
Prior work on generating OCL from natural language has progressed from rule-based pipelines to learning-based
and, more recently, LLM-based methods [ 1, 2, 4, 32]. A central challenge across this line of research is to produce
specifications that are not only syntactically valid, but also consistent with the target model context and usable at the
granularity required in practice, namelyoperation contractsrather than isolated statements or expressions. Table 1
summarizes representative approaches and highlights the distinction that motivates this paper: prior methods primarily
address generation quality, whereas Contract Gen couples generation with compilation, agentic revision, and execution
tests.
Rule- and pattern-based approaches.Early studies commonly relied on handcrafted linguistic rules, templates, or
intermediate formal representations. Bajwa and Shahzada compared NLP-based and pattern-based OCL generation
strategies and proposed an SBVR-based pipeline for mapping natural-language constraints into semi-formal representa-
tions that can later be transformed into OCL [4]. These approaches demonstrate feasibility, but they typically assume
relatively structured inputs and still require substantial manual proofreading in realistic scenarios [4].
Learning-based methods reduce manual engineering effort and relax restrictions on input form. DeepOCL by Yang
et al. generates OCL constraints from unstructured natural-language descriptions, improving flexibility over rigid
rule-based pipelines [ 32]. However, such methods may still suffer from context-related inconsistencies, including
invalid navigation paths, mismatched scopes, and type misuse, and they remain primarily focused on statement-level
constraints rather than full operation contracts [32].
LLM-based generation and prompt engineering.The emergence of large language models has substantially improved
the synthesis capability for formal and code-like artifacts [7]. Abukhalaf et al. studied OCL generation with Codex and
showed that prompt design has a significant effect on output quality [ 1]. PathOCL further improves prompting by
injecting path-based model context for GPT-based OCL generation [2], and tools such as ChainForge support systematic
prompt exploration and comparison in LLM-based workflows [ 3]. Nevertheless, one-shot prompting can produce

2.2 Iterative Refinement, Agentic Generation, and Reliability
A second line of related work concerns how to improve the reliability of LLM outputs through decomposition, iterative
reasoning, and structured feedback. This line is particularly relevant because OCL contract generation is not merely a
text generation task: it also requires consistency with metamodel context, type rules, and executable semantics.
Reasoning decomposition and agentic workflows.Chain-of-Thought prompting and self-consistency have been shown
to improve performance on complex reasoning tasks by decomposing intermediate steps and reducing brittle single-pass
decisions [15, 26, 27]. More broadly, recent agentic frameworks suggest that complex generation tasks can benefit from
role decomposition, tool use, and iterative decision making rather than one-shot prompting [22, 25, 33, 34]. These ideas
motivate decomposing OCL contract synthesis into specialized roles for drafting, checking, and revision.
Reliability limitations of one-shot generation.A large body of evidence shows that LLM-generated code may be fluent
yet incorrect, incomplete, or hallucinated [7, 13, 14]. This observation directly applies to OCL: a generated contract may
look plausible while remaining ill-typed, context-inconsistent, or semantically incorrect during execution. Improving
reliability therefore requires not only better prompts, but also structured validation signals that can support targeted
revision.
From detection to revision-oriented feedback.Execution-based validation is more aligned with practical usability than
surface-level textual similarity alone. However, merely detecting that a generated artifact fails is often insufficient for
iterative refinement. To support stable revision, the system should indicate where the failure occurs and, ideally, which
clause or sub-expression is responsible. This requirement is particularly important for OCL contracts, where a local
mistake in a predicate, navigation, or quantifier can invalidate an entire precondition or postcondition.
This paper adopts decomposition and feedback for a narrower purpose: contract synthesis over a formal language
with executable semantics. Contract Gen combines structured LLM-based generation with validation signals from
parsing and TypeScript-based checking, so that failed candidates can be regenerated under explicit diagnostic guidance
rather than through unconstrained repeated prompting. OCLTSVM further provides localized runtime diagnostics,
which makes execution outcomes more interpretable and motivates future extensions toward tighter revision loops.
2.3 OCL Translation, Compilation, and Execution Backends
Executable support for OCL has long been important in model-driven engineering, where OCL is used to express
constraints, queries, and derivation rules [ 9, 11, 17]. In practice, translating OCL into executable artifacts such as
bytecode or target-language code remains a common strategy for runtime checking and downstream integration
[12, 20, 29, 31]. However, many existing solutions remain closely tied to specific technology stacks and are not designed
primarily to provide revision-oriented feedback for closed-loop generation workflows. Table 2 compares representative
OCL-to-code toolchains.

Java bytecode for efficient JVM-based execution [29]. RM2PT by Yang et al. employs Xtext for OCL syntax definition
and Xtend templates for code generation, translating OCL constraints into Java service interfaces and implementations

Common limitations and motivation.Across execution-oriented approaches, two recurring limitations remain. First,
semantic fidelity is often fragile for richer OCL constructs such as collections, navigation, and undefined handling. Second,
runtime diagnostics are usually coarse-grained, often indicating only that a contract failed rather than pinpointing the
responsible sub-expression [12, 20, 29, 31]. These limitations matter even more in our setting because verification-driven
contract generation depends on a backend that is not only executable, but also informative enough to support iterative
revision. Accordingly, OCLTSVM is positioned in this paper not as a standalone OCL execution engine, but as a
validation backend that enables execution-grounded and localized feedback for Contract Gen.
The missing link is not another standalone prompt template or another standalone execution engine. What is needed
is a workflow in which generation, executable checking, and diagnostic feedback are connected at the level of operation
contracts. Contract Gen addresses this intersection by combining multi-agent generation with executable validation
and diagnostic feedback forcontract-level,verification-driven, andrevision-orientedOCL synthesis.
3 Approach
3.1 Overview
Contract Gen turns a natural-language operation requirement into an executable OCL operation contract through
a verification-driven repair loop. The input to the workflow consists of the user’s natural-language description, the
operation signature, the project model context, transformation rules, prompt guidance, and previously collected
diagnostic evidence. The output is not only a generated OCL contract, but also a validation report that records whether
the candidate survives parsing, OCL-to-TypeScript translation, TypeScript checking, and Jest-based execution.
Figure 1 summarizes the project workflow. The upper part of the workflow produces an initial contract candidate
from the requirement and project guidance. The lower part validates that candidate through deterministic stages. When
the OCL parser or TypeScript checker rejects a candidate, the corresponding diagnostic message is classified, collected,
and returned as guidance for the next generation attempt. The loop is bounded by a fixed attempt budget, so the
framework treats repair as controlled verification-guided synthesis rather than unconstrained repeated prompting.

The workflow contains four agent-level roles. TheOCL Generatorinterprets the natural-language requirement and

distinct from the JVM-based OCLVM proposed in prior OCL tooling work; we use the name here to emphasize the
virtual-machine role of our backend in the Contract Gen pipeline. USE is not part of the generation loop. It is used only
in the evaluation as an external UML/OCL checker for sanity-checking whether OCLTSVM’s parser-level acceptance is
broadly consistent with an independent OCL front end.

3.2 Running Example: LibraryborrowBook
To illustrate the workflow on a richer operation-level contract, we use the libraryborrowBook(uid: String, barcode:
String): Boolean operation as a running example. In this case, a librarian scans a user identifier and a book-copy
barcode to process a borrowing request. The operation is useful as a running example because it involves several
interacting model elements, including User, Student, Faculty, BookCopy, Reserve, Loan, and Librarian. It also
combines multiple classes of obligations: object lookup, user eligibility checking, reservation handling, new loan
creation, book-copy status update, user loan-count update, and final result validation. The example shows how the
requirement and model context are converted into OCL candidates, how parser feedback repairs malformed clauses, how
the parser-ready contract is translated into TypeScript, and how the final execution step exposes a runtime navigation
defect that remains to be repaired.
Natural-Language Description ofborrowBook
Definition:A librarian scans a user ID and a book barcode to process a borrowing request.
Precondition:The system first checks whether the user exists, is not suspended, and still has borrowing quota.
Postcondition:The system then confirms that the selected copy is available, or reserved for this same user, creates
a new loan record, sets the due date by user type, updates the book status to loaned, and returns true when the
checkout succeeds.
Step 1: example input.The run starts from two inputs: the user’s natural-language borrowing requirement and
the system context. The requirement in the box above provides the operation-level intent and separates the expected
behavior into definition, precondition, and postcondition cues. The system context supplies the operation signature,
borrowBook(uid: String, barcode: String): Boolean, and the relevant classes, associations, and status fields.
Step 2: OCL generation.Given the natural-language requirement and the model context, the OCL Generator extracts
the operation-specific objects and obligations. For borrowBook, the generated definition binds the user identified by
uid, the book copy identified by barcode, and an open reservation for the same user and copy when one exists. The
resulting candidate separates the contract into adefinition, aprecondition, and apostcondition. At this stage, Contract
Gen treats the candidate as a hypothesis to be validated, rather than as a correct contract. The following three code
boxes show the initial clause-level outputs produced by the OCL Generator before parser feedback in the recorded
borrowBook run. They are presented one by one because each clause plays a different role in the later validation stages.

3.3 Contract Gen: Verification-Driven Multi-Agent Synthesis
In Contract Gen, generation is allowed to fail, but each failure must leave evidence that can constrain the next attempt.
The framework couples multi-agent LLM-based contract generation with validation stages, grounding revision in parser
and TypeScript diagnostics rather than surface-level textual plausibility. This use of diagnostic state follows the broader
motivation of agentic and tool-using LLM workflows [22, 25, 33], but specializes the loop to OCL contracts.
Given a natural-language operation requirement, its signature, and the corresponding model context, Contract Gen
aims to synthesize an OCL operation contract consisting of definition, precondition, and postcondition clauses. The
output is accepted only if it can be parsed as OCL, translated into TypeScript, checked statically, and executed under
the associated validation tests. Thus, the framework optimizes for executable validity rather than textual similarity
alone, following the same principle used in executable evaluation of generated code [7, 14].
As shown in Figure 1, Contract Gen is organized as a compact closed loop with four generation and validation
roles. The workflow starts from a natural-language operation description and project guidance. The guidance includes
project context, transformation rules, prompts, and operation-level metadata. In particular, the transformation rules
specify how accepted OCL constructs are lowered into TypeScript. These artifacts are reused as shared guidance for the
next candidate rather than as one-off prompt context. The roles share the same contract state but operate at different
abstraction levels. We describe them separately because this separation is central to the method: the first role proposes
OCL content, the middle roles convert and validate this content, and the final checking role turns compiler-level
evidence into actionable repair guidance.
(1) OCL Generator.TheOCL Generatoris the only role that directly interprets the user’s natural-language require-

failed attempts. Its task is not to emit a free-form explanation, but to produce a structured contract candidate with three
fields:definition,precondition, andpostcondition. The definition field introduces intermediate bindings, the precondition
field states when the operation is allowed to execute, and the postcondition field states the intended state transition and
return value. Figure 2 shows this role as the semantic entry point of the workflow.

validation evidence.

3.4 OCLTSVM: Execution-Grounded Validation Backend
OCLTSVM serves as the validation backend of Contract Gen. Whereas Contract Gen defines the agent-level synthesis
loop, OCLTSVM defines the deterministic backend that judges whether a candidate contract can be parsed, lowered,
statically checked, and executed. Its role is therefore not to generate new requirements-level content, but to turn
generated OCL into executable evidence and structured diagnostics. Compared with prior executable OCL backends
such as the JVM-based OCLVM by Willink et al., RM2PT, CrossEcore, and .NET-based OCL compilation, the OCLTSVM
backend in Contract Gen is designed as a lightweight Web-oriented validation backend that can be called repeatedly
inside a closed-loop generation-and-revision workflow [12, 20, 29–31].

Backend responsibility.OCLTSVM takes an assembled OCL operation contract as input and returns either validation
evidence or stage-localized diagnostics. Internally, it realizes three backend functions:
(1) parsing the OCL contract into a typed abstract syntax tree (AST)
(2) translating the AST into executable TypeScript using explicit mapping rules and a supporting runtime library
(3) validating the generated code through static checking and dynamic execution.
These functions correspond to the parser, TypeScript generator, TypeScript parser, and runtime-test components
embedded in the overall workflow in Figure 1. Contract Gen decides when and how to revise a candidate; OCLTSVM
decides what evidence that candidate provides at each validation boundary.
Parsing and intermediate representation.We implement the front end using ANTLR4 and transform parse trees into a
typed AST via a visitor-based pipeline [19]. The AST explicitly represents OCL constructs relevant to contract execution,
including navigation, iterator expressions, collection operations, conditionals, and Boolean connectives defined in OCL
[9]. At this stage, parser-level diagnostics such as line/column information and error messages can be collected and
returned as structured feedback.
Semantics-aware translation.From the AST, OCLTSVM generates TypeScript through a dedicated mapping strategy.
The translation preserves three kinds of OCL semantics needed for contract validation. First, it maintains type behaviour
for primitive types, user-defined types, and undefined values. Second, it preserves collection-valued navigation and
iterator operators. Third, it preserves control behaviour, including short-circuit Boolean evaluation and conditional
branches.
The target language is TypeScript, which provides a typed checking layer before execution [6, 23].
To support these mappings, OCLTSVM provides a lightweight runtime library for OCL-standard operations that do
not directly correspond to native JavaScript/TypeScript constructs, such as definedness checks, type predicates, selected
collection helpers, and contract-oriented utility functions. Temporal expressions are implemented through Day.js-based
support in the runtime layer [16]. This design keeps generated code compact while centralizing semantic corner cases
in the runtime layer.
Representative mapping categories.The mapping rules cover several representative categories needed for executable
operation contracts, including predefined OCL operations, collection operators, temporal expressions, iterator constructs,
and contract-specific state references such as self, result, and @pre. Rather than relying on ad hoc string-level
rewriting, OCLTSVM translates these constructs through explicit syntax- and semantics-aware rules so that generated
contracts can be validated under executable criteria. We distinguish between expression-preserving translation rules
and post-state effect realization rules. The former translate OCL expressions into TypeScript expressions for checking,
whereas the latter operationalize generated postcondition obligations in the executable validation artifact. These
effect-realization rules are not intended as denotational definitions of OCL side effects; they describe how the validation
harness realizes or checks state changes required by generated operation contracts.

Validation modes.OCLTSVM combines static and dynamic validation. Static validation uses TypeScript parsing,
compilation, and type checking to detect malformed expressions, missing members, and incompatible types before
execution [6, 23]. Dynamic validation executes generated contracts under test scenarios and records concrete validation
outcomes through Jest-based tests [18]. Together, these two levels provide evidence not only that a contract fails, but
also whether the failure originates from parsing, translation, static checking, or runtime behavior.
Current feedback boundary.In the current implementation, parser diagnostics, TypeScript generation errors, and
TypeScript static diagnostics are integrated into the revision loop as structured revision signals. By contrast, Jest outcomes
serve as the final acceptance criterion rather than as automatically loop-integrated feedback. Parser and TypeScript
diagnostics drive automatic feedback-guided revision, whereas Jest outcomes and localized runtime diagnostics are
used to judge and interpret the final candidate. This boundary separates automatic repair evidence from final execution-
grounded acceptance evidence.

4 Evaluation
4.1 Research Questions
We evaluateContract Genfrom three complementary perspectives:
(1) whether it can generatesyntactically validOCL operation contracts
(2) whether the generated contracts remain valid underexecution-grounded validation
(3) whether structured diagnostics and iterative revision provide useful repair signals during generation.
Because the goal is not surface-form similarity butexecutable and verifiablecontract synthesis, and in line with
executable evaluation practices in code generation [7, 14], we study the following research questions:
RQ1 (Syntactic Validity).How effective is Contract Gen at generating syntactically valid OCL contracts before
execution-grounded validation?
RQ2 (Execution-Grounded Validation).How effective is Contract Gen at generating OCL contracts that remain
valid after translation, compilation, and execution-based validation?
RQ3 (Feedback Utility).How useful are parser- and TypeScript-level diagnostics for repairing failed intermediate
candidates within the bounded revision loop?

4.3 Dataset, Setup, and Protocol
We evaluate the approach on five representative case studies derived from formal requirements models, following the
same benchmark family used in RM2PT-style requirements prototyping studies [30, 31]. Table 3 summarizes the dataset.
Table 3. Dataset summary across five case studies.

The dataset is intentionally heterogeneous: ATM contains compact transaction-style operations, CoCoME and Library
Management contain richer object navigation, and Loan Processing contains several decision-oriented services. This
variation is important for the evaluation because the same generated contract must survive both parser-level checks
and executable validation across different modeling idioms. The following protocol therefore treats each operation as a
complete contract-generation task rather than as an isolated OCL expression.
For each operation, we run the full workflow:
(1) multi-agent contract generation with Contract Gen
(2) ANTLR-based parsing
(3) OCL-to-TypeScript translation
(4) TypeScript compilation/type checking
(5) Jest-based execution tests.
Each model is given the same generation budget of up to5attempts per operation. An operation is counted as
successful if any attempt yields a contract that passes the target criterion for the corresponding metric. This protocol
evaluates whether a method can reach a syntactically valid or executable contract within a fixed revision budget, rather
than whether every intermediate attempt is successful.
Execution backend.All validity and validation-success results are grounded in the OCLTSVM toolchain: generated
OCL contracts are parsed, translated to TypeScript, compiled, and executed under the corresponding unit tests. The
implementation relies on ANTLR4 for parsing [19], TypeScript for static checking [23], and Jest for dynamic validation
[18]. This setup evaluates not only textual plausibility but also execution-grounded reliability.

The feedback loop improves recoverability, but it also consumes attempts and latency when a model repeatedly
produces candidates that fail at different stages. The practical tradeoff is therefore not whether feedback is useful in
the abstract, but whether a backbone can use that feedback within a bounded budget. This observation frames the
summary below.
4.6 Summary of Findings
The results support three main findings. First, Contract Gen obtains higher syntactic validity than the reported results
of historical prompting baselines and, for the strongest variants, improves over the PureLLM direct-generation baseline
under our controlled setting, with several backbone models reaching full validity within the bounded revision budget.
Second, execution-grounded validation remains significantly harder than parser-level validity, and the comparison
with PureLLM shows that parser-level gains do not automatically translate into execution-level gains. Third, structured
diagnostics provide useful repair evidence, especially for models that can incorporate parser and TypeScript feedback
efficiently, but the benefit depends on the stability and latency profile of the backbone model.

5 Discussion and Threats to Validity
Implications for executable OCL contract synthesis.The central lesson from the evaluation is that parser validity and
executable validity should not be conflated. Across the benchmark, Contract Gen achieves higher parser-level validity
than the reported results of historical prompting baselines, while execution-grounded gains depend on the backbone
model. The most important observation is the gap between syntactic validity and execution-grounded success. Several
variants reach 100% parser-level validity, but only 45.61%–61.40% of the generated contracts pass the full executable
pipeline. Parser acceptance is therefore necessary but not sufficient; the main contribution is a closed-loop validation
framework rather than a prompt template alone. The diagnostic evidence in RQ3 further shows that structured signals
from parsing, TypeScript generation, and static checking are not merely auxiliary debugging information. They are an
essential mechanism for making iterative revision effective. This result supports the broader claim of the paper: reliable
contract-level OCL generation requires a loop that generates, validates, diagnoses, and revises candidate contracts,
rather than one-shot prompting alone. This view complements recent prompt-based and LLM-assisted OCL generation
studies [1, 2].
Dataset scale and external validity.Although the benchmark spans five representative RM2PT case studies and
multiple domains, it contains 114 operations in total [30, 31]. This scale does not fully capture the diversity of industrial
requirements, modeling styles, naming conventions, and ambiguity patterns. Moreover, our benchmark is drawn from
the RM2PT family rather than being fully identical to those used in all prior OCL-generation studies, which limits
strict head-to-head comparability. Accordingly, the PathOCL and Codex Prompt rows in the evaluation should be read
as historical reference points, while the strongest controlled comparisons are PureLLM and the no-feedback ablation
under the same dataset and validation pipeline. Future work should therefore evaluate the approach on larger and more
heterogeneous datasets, ideally including industrial artifacts and publicly reusable benchmarks.
Oracle quality and evaluation depth.Our correctness metric is grounded in translation, compilation, and Jest-based
execution tests, which is stronger than textual similarity alone and more consistent with executable evaluation practices
in code generation [7, 14]. However, it is still bounded by the quality of the available test oracles. The current evaluation
is mainly oriented toward functional scenarios and happy-path behavior, and therefore may underrepresent boundary
conditions, invalid states, exceptional flows, and concurrency-related behaviors. Even when statement and line coverage
are acceptable, subtle semantic defects may still remain hidden in under-tested branches. Future work should strengthen
the oracle through negative testing, fuzzing, metamorphic relations, differential testing, and broader scenario coverage.
Toolchain and model dependence.The reported results are obtained under a specific toolchain configuration, namely
OCLTSVM together with TypeScript and Jest, and performance also depends on the capabilities of the underlying LLM
family. Different runtimes, alternative OCL engines, or different model ecosystems may affect absolute performance.
Similarly, prompt sensitivity and domain-vocabulary mismatch may vary across LLM families, especially when moving
beyond the models considered in this study, a risk also observed in prompt-engineering studies for OCL and code
generation [1, 3, 28]. LLM nondeterminism is another source of variation. Even with fixed prompts and a fixed attempt
budget, API versions, decoding settings, service-side model updates, and transient generation failures can change
individual candidates. For this reason, we retain generated candidates, validation logs, and table-generation data so that
reported outcomes can be inspected at the operation and attempt level rather than only through aggregate percentages.
Broader evaluation across additional commercial and open-source models would improve external validity and clarify
how robust the framework is to different generation behaviors.

Coverage of translation rules and semantic corner cases.OCLTSVM is designed to preserve key OCL semantics,
including typing, collection behavior, and short-circuit evaluation, and Section 3 documents the detailed translation
rules. However, semantic preservation is bounded by the completeness of the mapping rules, the runtime library, and
the tests used to validate edge cases. The USE-based sanity check in Section 4 provides an external check for semantic
loading and type checking of generated definitions and preconditions across all 114 operations, but it does not by itself
establish full post-state behavioral equivalence. The few USE failures also illustrate how external OCL engines can
expose stricter interpretations of helper contexts, collection navigation, and collection typing. Fully characterizing
equivalence for all OCL 2.4 features and all modeling idioms remains challenging. This limitation is also consistent
with the broader difficulty of cross-platform OCL execution and implementation fidelity reported in prior OCL tooling
research [12, 20, 29]. Future work should therefore expand feature coverage, document unsupported constructs more
explicitly, and perform more systematic differential testing against reference engines.
Practical deployment considerations.Closed-loop multi-agent workflows introduce additional inference calls and
tool invocations compared with one-shot prompting, which may increase latency and cost in practical deployments.
In addition, some parts of the transformation from requirements models to executable artifacts still require manual
alignment between model elements and runtime data structures, which may limit reproducibility and scalability. Finally,
our current evaluation focuses on validity and executable correctness, but does not yet assess dimensions such as
readability, maintainability, revision locality, or developer trust through user studies. These factors are important for
real adoption and should be incorporated in future work together with budget-aware scheduling, caching, and more
automated model-to-code alignment.
Reproducibility.Independent inspection of the results requires more than the manuscript text. The evaluation depends
on prompts, model configurations, generated candidates, validation logs, test oracles, and the OCLTSVM implementation.
We have organized the benchmark operations, generated candidates, validation logs, USE sanity-check artifacts, and
table-generation data as replication materials for the study. The artifact should also include exact prompt templates,
model/backbone settings, parser and translation versions, and scripts for recomputing the reported tables. This is
particularly important because external baselines are reported from prior papers, whereas PureLLM and Contract Gen
results are produced by our own executable validation pipeline.
6 Conclusion
This paper addressed a practical challenge in model-driven engineering: generatingcontract-levelOCL specifications
from requirements in a way that is not only syntactically well formed, but also executable, verifiable, and amenable
to iterative improvement. To this end, we presentedContract Gen, a verification-driven multi-agent framework for
executable OCL contract generation. Contract Gen organizes synthesis as a closed-loop collaboration among four
agents:OCL Generator,Contract Generator,TypeScript Generator, andTypeScript Parser, combined with
parsing, translation, static checking, execution-based validation, and feedback-guided revision.
To support this workflow, we further developedOCLTSVM, a lightweight TypeScript-based validation backend that
translates OCL contracts into executable TypeScript while preserving key OCL semantics, including type discipline,
collection behavior, and short-circuit evaluation. By combining ANTLR-based parsing, semantics-aware translation,
compiler-level checking, and Jest-based execution, OCLTSVM provides execution-grounded evidence about whether a
generated contract is runnable under validation rather than merely plausible in form.
Our evaluation on 114 operations from five representative case studies shows that the proposed workflow improves
the reliability of OCL contract generation under our controlled setting and achieves higher syntactic validity than
